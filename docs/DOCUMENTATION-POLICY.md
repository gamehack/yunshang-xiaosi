# 代码与文档同步工作原则

**强制原则：代码与文档必须同步更新。** 适用于半日闲所有里程碑、修复、重构、性能优化、配置和部署变更。

## 每次改动的最低要求

- 功能、交互或界面变化：同步 README 的当前功能/状态，以及适用的视觉或交互规范。
- 架构、数据结构、模块或算法变化：同步 ARCHITECTURE.md，写清实现边界、取舍与未完成事项。
- 美术/场景变化：同步 VISUAL.md，说明已实现的视觉要素与目标视觉之间的差距。
- 发布/验收/部署变化：同步 CHANGELOG.md，分别记录代码提交、CI、Cloudflare 生产部署与真实设备测试；不得将任一项代替另一项。
- 仅内部代码格式调整且不影响行为：可以不改正文，但 PR 必须注明“文档无需变更”及原因。

## 开发门槛

1. 在 develop 上开发，同一 PR 内完成代码、测试和文档；可以分多次提交，但合并前必须齐备。
2. CI 通过后检查文档准确性。README 不得保留与现网版本冲突的描述。
3. 发布前核对版本记录，发布后补充生产部署及实测结果；未验证内容标为“待验证”。
4. 保留历史研究资料但明确标记其历史属性，不把过期设想当成现行需求。
5. 不以“后续补文档”为完成标准；如确需紧急 hotfix，应在同一 hotfix PR 同步最小文档并在下一批完善。

## PR 核对清单

- [ ] 代码及对应测试已更新
- [ ] README 当前功能与版本准确
- [ ] ARCHITECTURE.md 与 VISUAL.md 中受影响部分已更新
- [ ] CHANGELOG.md 记录变更及验证状态
- [ ] 未完成事项与验收范围明确
- [ ] 没有泄露密钥、私有数据或未授权资产

**自动化门禁（M1.4）：** PR 的 GitHub Actions 运行 `node scripts/check-docs.mjs`；如果 `src/`、`package.json` 或 `vite.config.ts` 有改动，要求同一 PR 至少更新 README 或 `docs/` 文件。该检查只验证同步变更存在，不验证文档语义正确；仍须人工/代码审查。
